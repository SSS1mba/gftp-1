# Протокол GFTP/1 (GMS Folder Transport Protocol)

## 1. Назначение

GFTP/1 — прикладной протокол для передачи одного файла или папки с файлами между клиентом и сервером по TCP. Протокол работает поверх `SOCK_STREAM` / TCP, использует сокеты Беркли/Winsock и не является WebSocket.

- **Транспорт:** TCP, IPv4 (`AF_INET`, `SOCK_STREAM`).
- **Порт по умолчанию:** задаётся в конфигурации, например `20010`.
- **Порядок байтов:** network byte order (big-endian). 16-бит — `htons()`, 32-бит — `htonl()`, 64-бит — собственная функция `htonll()` / `ntohll()`.

## 2. Общий формат кадра

Каждое сообщение состоит из фиксированного 12-байтного заголовка и payload.

| Поле | Размер | Описание |
|---|---:|---|
| `version` | 1 байт | Версия протокола. Для GFTP/1 = `1`. |
| `msg_type` | 1 байт | Тип сообщения (см. раздел 3). |
| `flags` | 2 байта | Зарезервировано, всегда `0`. |
| `payload_len` | 4 байта | Длина payload в байтах, без учёта заголовка. |
| `file_count` | 2 байта | Количество записей манифеста. Имеет смысл только для `FILE_MANIFEST` / `DIRECTORY_MANIFEST`, в остальных кадрах = `0`. |
| `reserved` | 2 байта | Зарезервировано, всегда `0`. |

Итого заголовок: **12 байт**.

Ограничения:

- `payload_len` ≤ 1 МиБ;
- блок `DATA.data` ≤ 64 КиБ;
- `file_count` ≤ 65535;
- `path_len` ≤ 4096.

## 3. Типы сообщений

| Значение | Имя | Назначение |
|---:|---|---|
| `0x00` | `FILE_MANIFEST` | Манифест передачи одного файла. |
| `0x01` | `DIRECTORY_MANIFEST` | Манифест передачи папки. |
| `0x10` | `DATA` | Блок данных файла. |
| `0x11` | `FILE_END` | Завершение передачи одного файла, содержит CRC32. |
| `0x12` | `TRANSFER_END` | Завершение всей передачи. |
| `0x20` | `ACK` | Подтверждение приёма. |
| `0x7F` | `ERROR` | Сообщение об ошибке. |

Типы `0x00` и `0x01` соответствуют исходной идее «0 — один файл, 1 — папка». Остальные типы — служебные.

## 4. Формат payload

### 4.1. `FILE_MANIFEST`

Заголовок: `msg_type = 0x00`, `file_count = 1`.

| Поле | Размер | Описание |
|---|---:|---|
| `path_len` | 2 байта | Длина имени файла. |
| `file_size` | 8 байт | Размер файла в байтах. |
| `path` | `path_len` байт | Имя файла в UTF-8, относительный путь без `..`, без абсолютного пути, без буквы диска. |

### 4.2. `DIRECTORY_MANIFEST`

Заголовок: `msg_type = 0x01`, `file_count` — количество записей в манифесте.

| Поле | Размер | Описание |
|---|---:|---|
| `root_name_len` | 2 байта | Длина имени корневой папки. |
| `root_name` | `root_name_len` байт | Имя передаваемой папки в UTF-8. |
| `entries` | переменная | `file_count` записей. |

Каждая запись:

| Поле | Размер | Описание |
|---|---:|---|
| `entry_flags` | 1 байт | Бит 0: `IS_DIR`. Остальные = 0. |
| `path_len` | 2 байта | Длина относительного пути. |
| `file_size` | 8 байт | Размер файла. Для каталога = 0. |
| `path` | `path_len` байт | Относительный путь в UTF-8, разделитель `/`. |

Правила путей:

- пути только относительные;
- запрещены `..`, абсолютные пути, буквы диска, `\` в качестве разделителя;
- сервер преобразует `/` в `\` при записи на Windows;
- пустые каталоги передаются записью с `IS_DIR = 1`, `file_size = 0`;
- `file_count` — количество всех записей, включая каталоги;
- `file_index` в `DATA` и `FILE_END` — индекс записи в манифесте; для каталогов `DATA` не передаётся.

### 4.3. `DATA`

| Поле | Размер | Описание |
|---|---:|---|
| `file_index` | 2 байта | Индекс файла в манифесте. |
| `offset` | 8 байт | Смещение блока в файле. |
| `data` | `payload_len - 10` байт | Данные файла, ≤ 64 КиБ. |

Передача файла идёт последовательными блоками с увеличением `offset`.

### 4.4. `FILE_END`

| Поле | Размер | Описание |
|---|---:|---|
| `file_index` | 2 байта | Индекс файла. |
| `crc32` | 4 байта | CRC32 всего файла в network byte order. |

CRC32 передаётся **всегда**. Сервер сравнивает его со своим значением, посчитанным при записи файла, и при несовпадении отвечает `ERROR 0x0005`.

### 4.5. `TRANSFER_END`

| Поле | Размер | Описание |
|---|---:|---|
| `status` | 1 байт | 0 — успешно, иначе код ошибки. |

### 4.6. `ACK`

| Поле | Размер | Описание |
|---|---:|---|
| `ack_type` | 1 байт | Тип подтверждаемого сообщения. |
| `file_index` | 2 байта | Индекс файла; `0xFFFF` — для манифеста или `TRANSFER_END`. |
| `next_offset` | 8 байт | Следующее ожидаемое смещение. |
| `status` | 1 байт | 0 — OK, иначе код ошибки. |

### 4.7. `ERROR`

| Поле | Размер | Описание |
|---|---:|---|
| `code` | 2 байта | Код ошибки (см. раздел 6). |
| `message_len` | 2 байта | Длина текстового сообщения. |
| `message` | `message_len` байт | Текст ошибки в UTF-8. |

## 5. Последовательность работы

1. Клиент устанавливает TCP-соединение с сервером.
2. Клиент отправляет `FILE_MANIFEST` или `DIRECTORY_MANIFEST`.
3. Сервер проверяет версию, пути, размеры и отвечает `ACK` с `ack_type = manifest`.
4. Для каждого файла:
   1. клиент читает файл блоками ≤ 64 КиБ, параллельно считает CRC32;
   2. клиент отправляет `DATA` с текущим `offset`;
   3. сервер пишет блок, считает CRC32 и отвечает `ACK` с `next_offset`;
   4. после последнего блока клиент отправляет `FILE_END` с итоговым CRC32;
   5. сервер сверяет размер и CRC32 → `ACK` либо `ERROR 0x0005`.
5. После всех файлов клиент отправляет `TRANSFER_END`.
6. Сервер отвечает `ACK` и закрывает соединение (либо ждёт следующий манифест — зависит от реализации).

Модель подтверждений — **stop-and-wait**: один `DATA` — один `ACK`
## 6. Коды ошибок

| Код | Значение |
|---:|---|
| `0x0001` | Неподдерживаемая версия протокола |
| `0x0002` | Некорректный кадр |
| `0x0003` | Недопустимый путь |
| `0x0004` | Ошибка записи на диск |
| `0x0005` | Несовпадение CRC32 |
| `0x0006` | Тайм-аут |
| `0x0007` | Слишком большой кадр |

При ошибке передача прекращается, отправитель может закрыть соединение. Получатель вправе удалить частично записанные файлы.

## 7. Отличие от FTP

GFTP/1 отличается от FTP по четырём пунктам:

1. **Бинарный формат протокола.** Все кадры имеют фиксированный 12-байтный заголовок и бинарные поля; управляющий канал FTP — текстовый.
2. **Одно TCP-соединение.** FTP использует два соединения (управляющее и данных), что создаёт проблемы с NAT/firewall и требует active/passive mode.
3. **Транзакция на уровне папки.** Вся папка — единый сеанс; при ошибке сервер может откатить частично записанное. В FTP `mput` — набор независимых `STOR`.
4. **Manifest-first.** Клиент сначала отправляет полное дерево (имена, размеры, флаги каталогов), и сервер проверяет пути, место и конфликты **до** записи данных. FTP узнаёт структуру по мере поступления файлов.

Дополнительно GFTP/1 обеспечивает end-to-end проверку целостности каждого файла через CRC32 и сохраняет пустые каталоги через флаг `IS_DIR`.
